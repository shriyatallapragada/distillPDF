# DistillPDF — NotebookLM chat to study-ready PDF

A local-first pipeline in two halves: a Chrome extension captures the answers
you choose from a NotebookLM chat and sends them straight to a local helper,
which runs four Python stages and writes `study-notes.pdf` and
`study-notes.html` to your Downloads folder. No intermediate file appears on
your desktop. A verification stage writes `report.json` inside the build.
User prompts are dropped in plain code, answers are kept verbatim, and math,
code, tables and diagrams are rendered by a real browser. Nothing is sent
anywhere. The same `chat.json` format is still the contract between the
capture and pipeline stages for the command line and the mobile page.

## Architecture

```
NotebookLM chat page
      │
      ├── desktop Chrome ── extension/ ── background.js ── native helper
      │                                   (build PDF + HTML directly)
      └── phone / tablet ─ mobile/capture.html ── chat.json
      │
      ▼
pipeline/clean.py          Stage 2  chat.json → clean.md + clean.meta.json
      │                              drop prompts, restore known answers, protect tokens
      ▼
pipeline/enhance.py        Stage 3  clean.md → enhanced.md + enhance.meta.json
      │                              one optional Ollama call per answer
      ▼
pipeline/render.py         Stage 4  enhanced.md → study-notes.html → study-notes.pdf
      │                              self-contained HTML, headless Chrome print
      ▼
pipeline/validate.py       report.json + contact-sheet.png
```

Each stage reads one file and writes the next, so any stage can be re-run on
its own. The native helper (`scripts/native_host.py`) runs all four stages in a
temporary folder and copies only the finished PDF and HTML to Downloads, which
keeps Chrome's 1 MB native-message limit out of the way. The contract between
capture and Stage 2 is just the `chat.json` format described below. All
CSS/JS/fonts used by the HTML are vendored locally; the renderer does not need
a network connection.

## Install

Python 3.10+ and desktop Chrome are required for the renderer. Ollama is
optional; `--offline` skips all model calls.

One command from this directory:

| Platform | Command |
| --- | --- |
| macOS / Linux | `./install.sh` |
| Windows | `install.bat` (or `powershell -File install.ps1`) |

That creates `.venv`, installs the package with dev extras (using `uv` when
available, otherwise the platform's `venv` + `pip`), registers the local
native helper with the browser, and rebuilds both downloadable ZIPs. Manual
equivalent:

```bash
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python -e ".[dev]"
python3 scripts/install_native_host.py
python3 scripts/package_extension.py
```

On Windows, replace `.venv/bin/python` with `.venv\Scripts\python.exe`.

### Desktop extension (Windows, macOS, Linux)

Run the installer above once so the browser can find the local helper. Then
load the unpacked extension:

1. Open `chrome://extensions`.
2. Enable **Developer mode**.
3. Click **Load unpacked** and choose this project's `extension/` folder (or
   the unzipped `dist/DistillPDF-extension.zip`).
4. Open a NotebookLM chat; the picker appears on the right.
5. Tick the answers you want and click **Build PDF + HTML**.

`study-notes.pdf` and `study-notes.html` are written straight to your Downloads
folder — there is no `chat.json` step. If macOS denies the helper access to
Downloads, the files land in this project's `out/` folder instead and the
picker tells you where they went. Reload the extension once after running the
installer so it picks up the native host registration.

Answers start **unchecked**. Tick only the ones you want, or use **Select all**.
Short greeting/closing replies ("How can I help?", "Let me know if…") are
dropped automatically, so only study material reaches the PDF.

### Phones and tablets

Mobile Chrome and Safari cannot install MV3 extensions. Use
`dist/DistillPDF-mobile-capture.zip` instead: unzip it, open `capture.html` in
any mobile browser, paste each answer, and download `chat.json`. It works
offline, keeps drafts in local storage, and offers a **Copy JSON** fallback if
the browser blocks downloads. Move `chat.json` to a computer running
DistillPDF to produce the PDF. The generated `study-notes.html` is responsive
and opens directly on a phone.

## Use

### No command needed

On desktop, the extension's **Build PDF + HTML** button does the whole job; no
terminal is involved. The launchers below are for a `chat.json` you already
have (for example from the mobile page). Double-click the one for your system:

| System | Launcher |
| --- | --- |
| macOS | `make-pdf.command` |
| Linux | `make-pdf.sh` |
| Windows | `make-pdf.bat` |

It finds `chat.json` in `Downloads` (or next to the project), runs all four
stages, and opens `study-notes.pdf` automatically. You can also **drag
`chat.json` onto the launcher**. On the first run it performs the setup above
by itself. If Ollama is unavailable it quietly falls back to plain headings.

### Command line

```bash
# Export the picked answers from the extension as ~/Downloads/chat.json
nlm-pdf all ~/Downloads/chat.json --outdir out --offline

# Or allow one local Ollama call per answer
nlm-pdf all ~/Downloads/chat.json --outdir out
```

Individual stages are independently runnable:

```bash
.venv/bin/python -m pipeline.clean      chat.json out/clean.md
.venv/bin/python -m pipeline.enhance    out/clean.md out/enhanced.md --offline
.venv/bin/python -m pipeline.render     out/enhanced.md out/study-notes.pdf
.venv/bin/python -m pipeline.validate   out/study-notes.pdf
```

Open `out/study-notes.pdf` for printing, or `out/study-notes.html` as the
self-contained fallback (it also works on phones). On Windows use
`.venv\Scripts\python.exe` and `.venv\Scripts\nlm-pdf.exe`.

## Input contract

If you already have a plain Markdown answer, wrap it without editing the text:

```bash
.venv/bin/python scripts/markdown_to_chat.py test_txt/sample_chat.md \
    test_txt/sample_chat.json --title "QC notes"
```

`chat.json` is either a bare array of turns or an object with a `turns` array:

```json
{
  "title": "Optional notebook title",
  "source": "Optional NotebookLM URL",
  "user_instructions": "Optional: group by topic, bold definitions, ...",
  "turns": [
    {"role": "user", "markdown": "...", "index": 11},
    {
      "role": "assistant",
      "markdown": "## Topic\n\nFormula: $E = mc^2$\n\n| A | B |\n| --- | --- |\n| 1 | 2 |",
      "latex": ["E = mc^2"],
      "index": 12
    }
  ]
}
```

`role`, `markdown` and `latex` (optional KaTeX annotation sources) are the
fields the pipeline consumes. `index` and `user_instructions` are carried
through for traceability. User turns are discarded in Stage 2; a recovered
`latex` entry missing from the markdown is appended as display math.

## Stage guarantees

**Stage 2 — clean (deterministic).** Normalizes whitespace, bullets and Unicode
spacing artifacts; strips numeric citations when configured; folds `\(...\)` /
`\[...\]` into `$` / `$$` and promotes multiline/environment math (such as a
`bmatrix`) to display math; merges answers in chat order; swaps every formula
and code span for a global-unique `@@NLMDF_*@@` token. `clean.meta.json` stores
the originals and expected formula/table/diagram counts.

**Stage 3 — enhance (one Ollama call per answer).** Ollama is **optional** and
does only two things: suggest a short topic heading and, when prose describes a
process, add a Mermaid flowchart. It never rewrites your sentences — the prompt
forbids it, and output is accepted only if every protected token appears exactly
once unchanged, word loss stays within `max_word_loss` (default 5%), and every
Mermaid block parses with the bundled Mermaid build. Anything else falls back
to the original answer with a plain numbered heading; `enhance.meta.json`
records each fallback and why. `--offline` bypasses the model entirely, and an
unreachable or missing model is detected up front and treated the same way.

**Stage 4 — render.** markdown-it handles tables, strikethrough, footnotes and
heading anchors. Math and symbol runs use the same static-SVG technique as the
circuits: one monospace `<text>` per line pinned with `textLength`, so bras/kets,
Greek letters and box-drawing glyphs all sit on a fixed grid instead of relying
on KaTeX's HTML/MathML (which mangled NotebookLM's plain-unicode symbols). LaTeX
commands are converted to readable unicode text; matrices become aligned rows;
prose accidentally fenced as math (e.g. `10 Marks`) stays ordinary text.
Mermaid blocks become SVGs. Wide ASCII circuits become one viewBox-fitted SVG
per block with one `<text>` per source line, so they scale to page width without
wrapping. Connector rows that a chat export collapsed into `│ │ │` are rebuilt
under the matching control symbols, so multi-control Toffoli diagrams keep every
vertical connection; single-control diagrams still centre the `│` under `■`.
The HTML is fully self-contained; the PDF is printed through headless Chrome
with A4 break rules.

**Whitespace contract for diagrams.** Raw answer text is never trimmed or
whitespace-collapsed before Markdown parsing. Tabs become four columns inside
fenced code/ASCII blocks (`tab-size: 4` in CSS too); non-breaking spaces stay in
diagrams for alignment but fold to normal spaces in prose so it can wrap.
Prose, list items and table cells use `white-space: normal`, while `pre` /
`pre code` use `pre-wrap`; line breaks come from the Markdown parser, never a
separate `<br>` pass. When a message contains a diagram, the extension logs the
exact `JSON.stringify` of the raw text and the block's HTML next to the
converted Markdown in DevTools (also available for any message with
`NLMDF_DEBUG_WHITESPACE = '1'`).

**Verification — `validate.py`.** `report.json` covers rendered formula count,
Mermaid parse/render success, table count, diagram fit, diagram connection,
prose/symbol survival, and a manual visual contact sheet. Failed checks mark
the PDF as failed and point to the HTML fallback.

## Configuration

See `config.yaml`. The model is one setting, so swapping Qwen and Llama never
touches code. On a 16 GB Mac mini M4, start with an 8B model — larger models
crowd out the browser renderer. Qwen 3 uses `/no_think` by default
(`enhance.no_think: true`).

### Is Ollama connected?

```bash
.venv/bin/nlm-pdf doctor
```

It prints `ollama : OK …` or tells you exactly what is wrong (server down, or
model not pulled, with the `ollama pull` command to fix it). The same check runs
automatically before enhancement, and its result is saved in
`out/enhance.meta.json` under `ollama`. You do **not** need Ollama for a correct
PDF: without it, Stage 2 already wrote a numbered heading and your text is kept
verbatim. Install it only if you want Mermaid diagrams suggested from prose.

To install it: `ollama pull qwen3:8b`, then leave Ollama running in the
background. `nlm-pdf all …` will use it; `--offline` or the launchers will skip
it if it isn't there.
